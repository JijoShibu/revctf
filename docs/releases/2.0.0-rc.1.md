# RevCTF 2.0.0-rc.1

**Prepared preview — not published.**

Author: Jijo Shibu <jijoshibu@gmail.com>

This preview focuses on trustworthy results when a scan runs into limits. Interrupted
challenge containers are cleaned up and checked, captured output stays available, and
unfinished analysis is clearly marked. It is still a helper for reverse engineering;
finding a flag-shaped string does not prove a challenge is solved.

## What changes for you

- Allocate at least **4 GB (4096 MB)** to Kali. RevCTF accepts 3891 MiB or more of
  Linux-reported total RAM to allow for reserved memory. Below that, or when RAM cannot
  be measured, scanning stops unless you pass `--allow-low-memory`. Help and version
  remain available. A dry run shows whether a real scan would be blocked.
- A failed or partial requested stage returns **exit code 2**. Useful evidence stays in
  the report folder, other stages normally continue, and `--strict` stops early.
- `--maxmem-ghidra 1024M` now means a checked 1024 MiB analysis heap with a 1280 MiB
  whole-process allowance. Supporting memory is additional to the requested heap.
- Output limits use 1024-byte units and apply inside Docker too. They are per raw file,
  not a total disk budget. Reaching a limit does not trigger an automatic rerun.
- Every candidate remains **UNVERIFIED** until the known answer or the challenge's own
  acceptance check establishes that it is correct.

Earlier fixes in this preview protect input and report files, improve encoded-text
recovery, preserve analysis failures, and load custom Ghidra scripts from their folders.
The clean-install rehearsal also found a missing Java dependency. Installation now
explicitly includes the Java 21 development kit needed by Ghidra and retries interrupted
Ghidra downloads within a time limit.

## Evidence and limits

The [validation record](../reliability-validation.md) lists results and outstanding gates.
Controlled Ghidra checks recovered a known password at 512, 768 and 1024 MiB, and an
independent test supplied that password to the challenge and received its success reply.
This does not mean RevCTF itself automatically confirms arbitrary answers.

On the 4 GB test VM, median ordinary scans were nearly unchanged. Packed scans were
faster in the small sample. Ghidra scans varied: across both timing rounds their combined
median rose from 35.95 to 39.64 seconds. These figures are sample measurements, not a
general speed guarantee. Searches were not shortened to improve the numbers.

Operation at a real 2 GB allocation, current Ghidra 12.x integration, and automatic
solution of arbitrary challenges remain unverified or unsupported. Search limits can
still miss flags. Four gigabytes is a startup recommendation, not a completion guarantee.
SIGKILL and host crashes can prevent cleanup; an unreachable Docker daemon requires
following the saved recovery instructions.
